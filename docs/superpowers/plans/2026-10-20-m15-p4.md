# M15 P4 Implementation Plan (Tournament setup: game count + opponents list)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> **Every implementer and reviewer invokes `ponytail:ponytail` before writing or reviewing code** (global rule).

**Goal:** The admin sets how many games a tournament has when opening it (editable later); games 1..N exist from the
start, Finish pairs the next existing game, and the tournament ends by itself after its last game. Keepers and admins
see every game of the tournament as an editable opponents list. "That was the last game" (`p_last`) and "Add game
N+1" (`add_next_game`) are retired. Pick-notice emails keep working (spec §5.9, §8 P4: t312, t313).

**Architecture:** One migration (`0026_game_count.sql`): `open_tournament` gains a required `p_games`, `finish_game`
loses `p_last` and pairs game N+1 only if it exists, a new admin RPC `set_game_count` raises/lowers the count,
`reset_game` unpairs the next game instead of deleting it, `add_next_game` is dropped. The pick-email trigger
(`private.queue_pick_notice`, on `game_pairings` insert) is untouched: pairings are still inserted one game at a time.
Front end: `loadCurrentGame` returns the first unfinished game (not the newest row) plus the game count; GameControls
drops the last-game/add-game paths and gets the opponents list; StagesPanel gets the count at open and a count editor.
`core/tournament.ts` needs no logic change (`next` = 1 + newest started game; over = every game finished). Ships as
tag `m15-p4`.

**Tech Stack:** React 19 + react-router (hash), TypeScript, Supabase (PostgREST + plpgsql), Vitest + Testing Library, PGlite DB tests.

**Spec:** `docs/superpowers/specs/2026-10-19-m15-qol-design.md` §5.9, §6, §8 P4 (no papercuts were carried into P4), §9 amendments 1–5 (none touch P4).

## Rulings (bounded choices the spec leaves open — overturn any in review)

1. **Count range 1–20.** `open_tournament(p_stage, p_pairings, p_games int)`: `p_games` required (no default),
   `GAME_COUNT_INVALID` outside 1–20. The Open tournament form has a required "Games" number input, empty to start.
2. **Who sets the count:** admins only (`set_game_count`, Admin → Seasons → stage → Tournament). Keepers (and admins)
   edit opponents. Admin-power check: admins can open with any count, raise or lower it, rename opponents, undo games
   (M14), and the audit log records every count change `{from, to}`.
3. **`set_game_count(p_stage, p_count, p_pairings jsonb default null, p_provisional jsonb default null)`.** Lower:
   `p_count` ≥ the highest started game number (else `GAME_COUNT_INVALID`); games above it are deleted with their
   pairings (FK cascade) and opponent names; picks are keyed by number and stay (harmless; they come back if the count
   is raised again). Lowering to the number of the game that's live makes it the last game; lowering away an already
   paired next game is allowed (its pick emails already went out — acceptable, like a last-game tap today). Raise:
   games are appended. If the tournament was over (its last game finished), the first new game must be paired now:
   pairings are required and checked (`check_pairings`), the stage's `ends_on` must not have passed
   (`TOURNAMENT_ENDED`, as `add_next_game` today), and its pick emails go out via the trigger. Otherwise pairings are
   ignored. `NOT_OPEN` if the stage has no games yet. Same count = no-op without an audit row. Locks the stage's games
   (`for update`) so it can't race `finish_game` / `start_game`.
4. **`finish_game(p_game, p_pairings, p_provisional)`** (3 args again; `p_last` dropped): locks the stage's games; if
   game N+1 exists, `check_pairings` + insert its pairings (refuse `NEXT_GAME_EXISTS`-style double pairing: if N+1
   already has pairings, `NEXT_GAME_EXISTS`); if not, the pairings are ignored and the audit row says `last: true` with
   `pairings: null`. Returns N+1's id or null. The app sends `[]` for the last game.
5. **`reset_game`** (undo the newest started game): no longer deletes game N+1; it deletes N+1's pairings and N+1's
   `pick_next` outbox rows (`ref = N+1's id`), so the re-finish emails the (possibly different) pairing again, as
   today's delete-and-recreate did. Audit key `next_game_deleted` → `next_game_unpaired`. Slot clean-up from 0024 unchanged.
6. **`add_next_game` is dropped**; its gate entry, rpc helper, UI and error-only codes go (`NEXT_GAME_EXISTS` stays,
   used by Ruling 4). `GAMES_EXIST` stays for a second `open_tournament`.
7. **The tally's game** (`loadCurrentGame`): the stage's first unfinished game by number, or its last game when all
   are finished (the "is over" line). Returns `{ stage, game, count }` (`count` = number of games). The stage's
   last-day rule is unchanged.
8. **GameControls (tally list card):** Finish on a non-last game = today's preview + confirm. Finish on the last game
   (`n === count`) = `window.confirm("Finish game n? It's the last game: <stage> ends.")`, then `finishGame(id, [], [])`.
   Over: "<stage> is over after game n." with no button (raising the count is the admin's, in Admin). The single
   opponent field becomes **the opponents list (t313)**: one row per game, "Game k" + input (placeholder "e.g. Duke",
   maxLength 40) + Save, for every game, started or not, any time; drafts are per game id. On a live board
   (`sessionId` set) only Finish shows, as today.
9. **StagesPanel Tournament card:** summary "game n live/next of N" (or "over after game N"); a "Games" number input
   (min = highest started number, at least 1; max 20) + "Save count". Raising an over tournament first shows the new
   game's pairings in a `window.confirm` (`describePairings`, like Open), then calls `set_game_count` with them.
   Lowering needs no confirm (spec §5.9). Undo/Check pairings unchanged.
10. **Stats' "All stats" fold keeps listing every game** (unstarted ones already read "Not started"): with games
    pre-created it becomes the tournament's schedule with opponents. The League Games list (`TournamentCard`) already
    hides upcoming games; Admin → Leagues shows "Not paired yet" for them (fine).
