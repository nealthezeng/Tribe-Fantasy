**Goal:** Managers see live, unofficial scores and their players' stat lines while a game is played and until a keeper
verifies it: on the League matchup and game cards, and in the Stats table. The page refreshes itself (~15 s) while
such a game is on screen and the tab is visible, and what changed since you last looked shows as +N / −N chips and a
counting score (spec §5.3, §8 P6: t316–t319).

**Architecture:** One additive migration (`0028_live.sql`): a SECURITY DEFINER read RPC `live_game_taps(p_game)`
returning a started, unverified game's taps with an opaque per-game keeper number instead of keeper ids, for anyone
`can_read_league_data()` lets read league data. The browser feeds those rows through the existing `rowToTap` →
`liveStatLines` (`mergeTaps`, `tap_merge_seconds`) path, then scores with the existing scorer in provisional mode:
`buildLeagueTournament` adds `unofficial`, a map from each live/pending game to the same `GameOutcome` shape with
scores filled in and no W/L or standings delta, so the matchup and game cards just prefer it. Official standings,
tiles, past tournaments and pairing never read it. A `usePoll` hook reloads every 15 s while a game is live or
pending; a small `seen.ts` keeps the last-shown numbers per membership + game in localStorage for the chips. Tag
`m15-p6`.

**Tech Stack:** React 19 + react-router (hash), TypeScript, Supabase (PostgREST + plpgsql), Vitest + Testing Library, PGlite DB tests.

**Spec:** `docs/superpowers/specs/2026-10-19-m15-qol-design.md` §5.3, §5.2 (matchup shows each side's starters with
their stat line so far and points), §5.4 (Stats table includes the live game, marked), §4 anti-goal 2 (a live number
never looks final), §6 (DB phases go live between tournaments), §8 P6. No papercuts were carried into P6. §9
amendments 1–7: amendment 4 keeps the player page verified-only and says live numbers are P6's Stats-table job
(t318); the rest don't touch live data.

## Rulings (bounded choices the spec leaves open — overturn any in review)

1. **RPC:** `live_game_taps(p_game uuid) returns table (id uuid, athlete_id uuid, stat text, tapped_at timestamptz,
   undoes uuid, keeper int)`, `language plpgsql stable`. Gate: `private.require_user()` (anon never reaches it: no
   grant), then `if not public.can_read_league_data() then raise exception 'FORBIDDEN'`. Rows only for a game that
   has started and whose session exists and is unverified (`games.started_at is not null`, join `sessions` on
   `games.session_id`, `sessions.verified_at is null`) — live **or** finished-but-unverified. An unknown, null,
   unstarted, void (session deleted) or verified game returns no rows, not an error. Undo rows come back with their
   `undoes` link; the browser nets them (spec). `keeper` = 1, 2, … per game, numbered by each keeper's first tap in
   that game (`dense_rank() over (order by first_tap, keeper_id)`); taps whose `keeper_id` is null (removed accounts,
   M14) share one number, exactly as `rowToTap`/`verify_session` treat them. Ordered by `tapped_at, id`. No audit
   row (a read); listed with the read helpers in rpc-gate.
2. **"Live" means started and not verified** (status `live` or `pending` in the core). Only those games carry
   unofficial numbers; verified numbers replace them the moment `verified_at` is set ("lock when verified").
3. **Loading:** `loadLeagueRows(…, { live: true })` calls `live_game_taps` once per game whose session is unverified
   and started, and puts the rows in `rows.taps` with `session_id` = that game's session and `keeper_id` =
   `` `k${keeper}` ``. The staff `{ taps: true }` path (direct `stat_taps` select, used only by `seasonPairings` for
   Swiss pairing) is **left unchanged**: the pairing at Finish is the riskiest code in the app and gains nothing.
   Only the League tab (`TournamentCard`), the admin league browser and the Stats page load live taps; Leaderboards,
   team pages, the player page, needs-you dots and season ranks don't.
4. **`LeagueTournament.unofficial: Map<string, GameOutcome>`** (game id → outcome), built in `buildLeagueTournament`
   from `scoreTournaments(input, { provisional: true })` for every game whose official status is `live` or
   `pending`: the official outcome's `game` and `status`, with the provisional sides' `athleteScores`, `points` and
   `score`, and `delta: null`, `result: null`. Starters and factors are identical in both runs (they don't depend on
   scoring). Standings, tiles (Place/Record/Points), past tournaments and needs-you keep reading the official result.
   A starter with no taps scores `absent_score` (0 today) and reads "No stats".
5. **League (t317):** the matchup and every game card use `y.unofficial.get(id) ?? official`. Matchup for a started
   focus game: the scoreboard shows both scores (unofficial while live/pending), the strip adds a
   `<span className="pill warn">Unofficial</span>` next to "Live" / "Waiting on stats", and below the scoreboard each
   side's starters as rows "Name · 2 Goal, 1 Assist" (the game cards' existing wording) with their points (`fmt`), headed by the team name and its
   score; the same rows for a verified (final) focus game without the pill. Upcoming focus games are unchanged
   ("Your picks" / "Hidden"). Game cards: a pending game's scoreboard shows the unofficial scores (no W/L, no ±,
   pill stays "Waiting on stats") and its opened card shows the stat lines and points with the hint
   "Unofficial until a keeper verifies." in place of the factor hint.
6. **Polling:** `usePoll(reload, on)`: `reload()` every **15 000 ms** while `on` and
   `document.visibilityState === 'visible'`; when the tab becomes visible again (with `on`) it reloads at once and
   resumes; stops when `on` turns false, the tab hides, or the component unmounts. League: `on` = any of the league's
   games is `live` or `pending` and has pairings. Stats: `on` = any of the shown tournament's games is started and
   unverified. No polling anywhere else (admin league browser included: it reloads on open). A poll keeps the old data
   on screen (`useLoad` keeps `data`), so nothing flashes; a failed poll shows the usual error line until the next
   good one.
7. **Since you last looked (t319):** key `` `tribe.seen.${membershipId}.${gameId}` `` (the existing `tribe.` prefix),
   value `{ mine: number | null; them: number | null; points: { mine: Record<string, number>; them: Record<string, number> } }`
   (scores and per-starter points as shown, unofficial or verified). Only for a started focus game (not upcoming).
   On every load/poll: no stored value, unreadable or corrupt storage → no chips, no count, then store. Stored value
   differs → a chip on each starter row whose points changed by ≥ 0.01: `+N` (`.since.up`, gold) or `−N`
   (`.since.down`, `--error`), N = `fmt(|diff|)`; each changed score counts from the stored value to the new one;
   then store. A refresh with no change keeps the current chips; the next change replaces them. A starter missing
   from the stored side gets no chip. Write failures are ignored. Reduced motion: chips appear without motion and the
   score jumps. Keys are never cleaned up (one small key per team per game; `ponytail:` comment).
8. **Count-up:** `CountUp({ value, from })` renders `fmt` of a number moving from `from` to `value` with
   `requestAnimationFrame` over `--dur-count` (new token, **600ms**), read once via
   `getComputedStyle(document.documentElement).getPropertyValue('--dur-count')`; an unparsable/empty value
   (jsdom), `from === value`, or `matchMedia('(prefers-reduced-motion: reduce)').matches` → shows `value` at once.
9. **Stats table (t318):** `loadTournamentStats(seasonId, wanted, { today?, live? })`; with `live` (the season's
   `SeasonSettings`) it also returns `liveLines: LineRow[]` from `liveStatLines` over the tournament's started,
   unverified games (else `[]`), and `liveGames: number[]` (their numbers). StatsPage totals verified + live lines and,
   when `liveGames` is non-empty, shows above the table a `<p className="strip">` with the `.live` dot, "Live" and
   "Unofficial: includes game N" ("games 3 and 4" for two). The player page passes no `live` (amendment 4 stands).
10. **Admin powers:** admins and keepers read live data through the same RPC (any role passes
    `can_read_league_data`). The admin league browser loads live taps and its Games list adds, for a live/pending
    game, each pairing's unofficial score: "Zeal 6 – 3 Flow · Unofficial". Nothing to override (live numbers are
    derived; Verify stays the keeper tool). P6 has no destructive action (undo/confirm: none needed).
11. **Rollback is two lines in the runbook** (additive phase, no file): revert the code and push, then
    `drop function if exists public.live_game_taps(uuid);`. Nothing else changes in the DB, so no data is lost.
